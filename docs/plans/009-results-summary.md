# 009 成果總結：P0 到 P3

日期：2026-11-17。範圍：P0（既有實作對照）、P1（規格）、P2（單一匯流排）、P3（Bridge）。分發：公開 repo，不含任何客戶、場域或主機資訊。
各階段的細節與原始通過行在 `005` 到 `008`；本文件只彙整，數字不另行計算。

## 一、執行摘要

embnet-rs 要回答的是：借用 Cyphal 的設計、補上 Bridge 與 Polled link，能不能用一套介面串起嵌入式系統裡的各種匯流排，延遲多少、體積多少，出錯時的行為是否可預期。
P0 到 P3 完成了規格、協定核心、Native node 與 Bridge，並在模擬環境與一塊 NUCLEO-F767ZI 上驗證。

到目前為止的答案：協定本身的成本很低。不含 MAC 時，轉送一框約 500 個 CPU 週期，Node 只發佈的路徑占 4.7 KB 程式；
在板上以 1 Mbit/s 的 CAN loopback 量到單一匯流排的 p99 是 166 µs、經過 Bridge 是 330 µs，幾乎都是 Wire time。
五種通訊故障在模擬中全部被偵測，沒有錯誤資料交給應用；Bridge 在模擬中的延遲都落在建置期算出的上限內。

限制有兩項。第一，參考板沒有硬體 AES，軟體 MAC 驗證一則要 8,518 個週期，Bridge 不可能逐框驗證，只能驗跨 Trust zone 的 `protected` Subject，並由建置期檢查限制驗證率。
第二，目前只有一塊板子、沒有收發器、網路孔沒接線，兩個 Node 之間的真實 CAN、bus-off 與 UDP、UART 的實體 Link 都還沒驗證。

## 二、做了什麼

| 階段 | 產出 |
|---|---|
| P0 | 三個 Cyphal 實作的體積對照；Renode 對 STM32F767 的支援程度；相依授權清單（`005`） |
| P1 | 規格 0.2 版（`docs/spec/` 01 到 07）；獨立的 Python test vector 產生器，89 個案例；`embnet-core`；`embnet-config`（C1 到 C10）（`006`） |
| P2 | `embnet-node`；模擬匯流排的故障注入；fuzz；實板的每步週期數與 bxCAN 送出順序（`007`） |
| P3 | `embnet-bridge`；離散事件模擬與負載轉折點；實板 CAN1 與 CAN3 的 loopback 單跳延遲（`008`） |

程式碼：`crates/` 下四個 crate。三個執行在 MCU 上的 crate（`embnet-core`、`embnet-node`、`embnet-bridge`）都是 `no_std`、`forbid(unsafe_code)`、不配置記憶體，並開啟禁止 unwrap、panic、直接索引與可能溢位算術的 lint。

## 三、結果

驗證方法：**實測**是自己跑過量到的；**推導**是由實測值加公式算出；**查核**是讀規格或原始碼確認；**觀察**是看到行為符合但沒有量化。

| 項目 | 結果 | 方法 |

## 四、結論

1. 不含 MAC 時，協定的 CPU 成本遠低於預算：轉送一框約 500 週期，兩條滿載 CAN 時每框預算約 4,050 週期。
2. 在 1 Mbit/s 的 CAN 上，單跳延遲幾乎都是 Wire time。經 Bridge 的延遲約等於兩段單一匯流排相加，Bridge 的處理時間落在量測的抖動內。
3. 依優先等級計算的 network calculus 上限，在模擬的每一個情況都包住了量到的最大延遲，包括使用率接近 100% 時。UART 那條路徑的上限幾乎是緊的。
4. 高優先序的 Subject 不受低優先序流量影響：匯流排使用率從 12% 到 102%，`speed_cmd` 的最大延遲維持在 520 到 670 µs；低優先序的 `motor_state` 從使用率 72% 起變慢，102% 時最大延遲 998 µs。
5. 軟體 MAC 是唯一明顯的瓶頸，驗證一則約等於兩框的預算。
6. 模擬找出了一個只看文件看不出來的設計缺口：`protected` Subject 跨 Bridge 時 E2E Sync 不會跟著轉送。已修正並寫進規格。

## 五、建議

1. Bridge 的 MAC 驗證維持「只驗跨 Trust zone 的 `protected` Subject」，並以 C10 在建置期限制驗證率；需要更高驗證率的部署改用有 CRYP 的 STM32F777 或 F779。
2. 設定檔中 Bridge 的 `latency_us` 先維持 200 µs；P5 量到最壞中斷延遲後再收緊。
3. 下一步整理 `embnet-link-can` 驅動，把兩個實板問題（CANRX 上拉、清 TTCM）與「同一 session 同時只占一個 mailbox」的發送政策寫進去。
4. 硬體到位前，能在一塊板子上補的驗證有兩項：用 ST-LINK 的虛擬序列埠驗 UART 的實體 Link；用二極體把 CAN1 與 CAN3 的 TX 接成線與，驗真實的仲裁與 bus-off。

## 六、假設

| 假設 | 影響 |
|---|---|
| CAN 框長取最壞填充 80 + 10n 位元 | 建置期上限偏保守；實際框長通常較短 |
| Bridge 的處理延遲在模擬中取 200 µs | 模擬的延遲偏高；實板量到的處理時間小得多 |
| bxCAN 的 loopback 時序等同真實匯流排 | loopback 沒有收發器延遲與線上傳播，實際匯流排會略慢 |
| 板上量測以輪詢方式收發，沒有其他中斷負載 | 量到的是無干擾下的延遲；有其他中斷時 p99 會變大 |
| 模擬的發送時刻依規格的抖動定義（每筆落在排定時刻 ± jitter/2） | 不符合這個定義的應用，入口限流可能丟資料 |
| MAC 成本以 RustCrypto `aes` 0.9.4 的軟體實作量測 | 換實作或換晶片要重量 |

## 七、有效性的檢討

| 面向 | 在這裡的威脅 | 怎麼緩解 |
|---|---|---|
| 內部效度 | 板上的延遲包含輪詢迴圈本身的間隔，不全是協定與 Wire time | 同一支韌體量單一匯流排與經 Bridge 兩種情況，比較差值；Wire time 另以框長推算對照 |
| 外部效度 | 只有一塊板子、loopback、沒有其他 Node 搶匯流排；主機數字在非即時核心上量 | 報告中一律標明環境（`env=`）；真實多 Node 的數字等第二塊板子與收發器 |
| 建構效度 | 故障注入的「偵測」由我們定義；遺失以缺口數計，毀損只改資料與 E2E 欄位 | 各故障的注入與偵測定義寫在 `007` 第三節；注入數在注入端直接計數，不從偵測結果反推 |
| 結論效度 | 模擬只用一組 seed；fuzz 只跑 5 分鐘；p99 的信賴區間用常態近似 | 通過行附 seed、時數與語料庫大小；樣本數都達到 10,000 以上；fuzz 時數要在 CI 中拉長 |
